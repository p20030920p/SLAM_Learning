# Sim2Real 机器人建图与定位测试协议

[English](PROTOCOL.md) | 中文

测试采用 [Sim2Real-AlgoBench](https://github.com/p20030920p/Sim2Real-AlgoBench) 的机器人建模。目标是逐步观察点云建图、定位与恢复的失效条件，形成开放问题的证据。本文是测试设计，尚不代表各级场景已经完成实跑。

## 机器人与传感器

已核对本地上游提交 `53324d40def0dd753b4a99021b8fe596955a1ecd`。原模型为三轮全向底盘，URDF 和四个 STL 资产与该提交一致。[模型检查记录](robot-model.json)保存来源、文件哈希、关节与传感器配置；它是源码检查，不是仿真运行验收。

保留原底盘的几何、质量与惯量、轮关节、碰撞及驱动接口。不得换成另一种移动底盘后仍声称测试这个机器人。原导航配置使用 `nav2_amcl::OmniMotionModel`，并消费 `/omni_drive_controller/odom`；横向运动须纳入运动模型。

| 配置 | 点云来源 | 适用范围 | 状态 |
| --- | --- | --- | --- |
| 原生二维版本 | `/scan` 的二维激光点，经标定投影为平面点云 | 二维建图、固定地图定位；原配置 720 束、360°、10 Hz、0.08—12 m | 源码已核对，运行需单独验收 |
| 同底盘三维扩展版 | 独立安装的三维激光及 `PointCloud2` | 三维点云地图和三维方法适配 | v1 静态检查与静止点云源检查通过；移动／建图／定位待验收 |

原相机是 RGB `camera`，不是深度相机。二维点投影进 XYZ 容器并不会获得三维几何；不能将这种输入称为已完成三维激光测试。三维扩展只增加明确记录的传感器安装与外参，保留原底盘，并单独版本化 URDF、桥接、点频和标定。原论文复现仍使用作者数据，不受这里传感器选择影响。

三维 v1 采用 720×16 束、垂直视场 30°、10 Hz、0.08—12 m；安装在 `base_link` 上方 0.30 m，增加 0.05 kg 传感器组件。原底盘参数与传感器元素逐项保持，新增组件使整机总质量增加，应在版本间比较时记录。[URDF](../../config/robot_profiles/omni-3d-v1/omni_car_lidar3d.urdf) · [桥接](../../config/robot_profiles/omni-3d-v1/bridge_sensors.yaml) · [版本与静态检查](../../config/robot_profiles/omni-3d-v1/profile.json)。`/points` 桥接 Gazebo 的 `/lidar_3d/points`；不得假设有逐点时间戳或原模型有 IMU。

重生成入口：

```bash
python3 src/scripts/testing/create_robot_profile.py \
  --upstream-root /root/projects/Sim2Real-AlgoBench
gz sdf -p config/robot_profiles/omni-3d-v1/omni_car_lidar3d.urdf
```

运行前需使用原仓库已安装的机器人描述与控制包；这两条命令生成／解析模型，不会自动完成机器人测试或实时录制。

静止点云源检查入口（ROS Jazzy、Gazebo Harmonic、`ros_gz_bridge`、Xvfb 与已构建的原仓库）：

```bash
bash src/scripts/testing/verify_3d_source.sh
```

[本轮记录](t0-3d-source.json)：收到 15 帧，每帧 720×16 个有效点，字段为 `x/y/z/intensity/ring`，最后一帧 Z 向跨度约 1.88 m，仿真时间帧率约 10.01 Hz。这证明静止三维点云链可用；尚未测墙钟实时率、运动畸变、建图或定位。记录绑定模型、脚本与世界哈希。两次失败分别来自隔离脚本的[模型资源路径](t0-3d-source-attempt1.json)和[控制初始化顺序](t0-3d-source-attempt2.json)，保留以便接续排查。

## 先完成运行验收

检查实际数据而非配置期望：激光／点云帧率、有效点数、量程与视场，`map→odom→base→sensor` 坐标关系，时间戳、轮速、横向运动、碰撞与停止行为。记录节点运行参数与仿真时间／墙钟比例。渲染失败单列，不能仅凭话题频率称实时成片成功。

传感器观测用于建图和定位，Gazebo 真值用于评价与故障事件标注。真实世界模型可以提供评测参考，不能替算法填充未观测地图或提供定位答案。

## 三种测试链

| 测试链 | 固定与比较的内容 | 回答的问题 |
| --- | --- | --- |
| A 给定位姿点云建图 | 同一份原始点云、同一组位姿，对比原始与论文地图处理 | 地图过滤是否减少动态残影，是否误删有效静态结构 |
| B 固定地图定位 | 独立建图 A 与测试 B；同一测试输入在不同地图／定位器上回放 | 地图质量、观测模型与环境变化怎样影响定位和重定位 |
| C 估计位姿的建图与 SLAM | 使用算法自己估计的位姿；固定数据，比较轨迹和地图 | 前端匹配、位姿漂移和地图污染怎样相互作用 |

A 是受控建图测试，不叫完整 SLAM；B 是定位测试；C 才包含运动估计与建图的耦合。二维和三维测试、作者原配置和平台适配结果分开记录。三维地图投影后供二维定位使用，应标注其投影与信息损失。

## 逐步加难的顺序

| 阶段 | 场景与推进方式 | 建图观察 | 定位观察 |
| --- | --- | --- | --- |
| T0 接口与标定 | 静止、直行、转动和横移 | 点云坐标、运动畸变与同步 | 位姿／轮速一致性；先排工程错误 |
| T1 丰富结构静态环境 | 短路线到完整路线，建图／测试独立采集 | 结构保留、完整度、重复对齐 | 正常误差、正常可用率 |
| T2 动态物体 | 同一路线逐次增加物体数量，其他条件固定 | 动态残影与静态误删 | 匹配外点、漂移、失效比例 |
| T3 短暂强遮挡 | 固定物体数量，延长遮挡持续时间；随后解除 | 有效静态结构减少后的地图变化 | 遮挡期间是否失效，解除后能否恢复及恢复时间 |
| T4 几何退化 | 固定传感器，走廊变长或重复结构增加；随后返回丰富结构区域 | 沿弱约束方向的错位／重影 | 方向性漂移、错误匹配，约束恢复后的结果 |
| T5 持久结构变化 | 地图冻结后移动家具／改变隔断；逐档改变可见结构 | 旧结构与新观测冲突 | 旧地图下的失败与恢复范围 |
| T6 组合压力 | 单因素已测后，再组合动态、退化与结构变化 | 多种误差的叠加 | 各策略的适用边界与错误恢复 |

这是测试推进顺序，跨场景不预设难度一定单调。每一类内部逐档加大一个因素，再根据实际失效率和可观测性测量确定难度。传感器束数、量程、视场与噪声作为独立因素，不能一次同时改变后把结果全归因于几何退化。

## 地图变化与故障事件

大变动须发生在建图之后的测试世界中。记录哪些物体移动、哪些结构新增／移除，以及机器人实际可见的变化；全地图变动比例不能代替当前扫描可见变化比例。只编辑地图是地图误差对照，另列。

各环境交叉测试无注入、初值偏移与实际绑架。初值偏移只改变估计信念；实际绑架改变真实位置，还需检查里程计是否泄露位姿跳变。故障注入与环境类型分开，避免将任何大初值误差都叫动态环境失效。

短暂遮挡记录解除时刻；退化场景记录返回丰富结构区域时刻。分别统计“故障至恢复”与“有效约束重现至恢复”的时间。持续地图变化没有自然解除时刻，单独规定剩余未变结构和测试截止时间。

## 评价与公平对照

| 对象 | 应保留的指标 |
| --- | --- |
| 点云／地图 | 静态结构保留、动态残留、观测范围内的几何误差／完整度；原论文指标按原协议另报 |
| 定位／轨迹 | 全时段位置与角度误差、方向性漂移、失效比例；初始化与恢复阶段不能只靠排除预热后统计 |
| 恢复 | 持续恢复成功数／实际失效回合数、未恢复数、恢复时间、错误恢复、复发、人工干预次数 |
| 正常运行代价 | 误触发重置、正常场景不可用时间、正常精度变化 |
| 资源 | 实际时延、CPU／GPU、内存、粒子／点数、建图训练与在线定位耗时分别记录 |

仿真源点的静态／动态标签和参考几何须先验证。只对确实被观测的区域评价地图完整度；空缺不能用世界几何补齐。原始未处理地图必须保留，防止只报告算法间的比较。

同一配置共用数据、路线、场景种子与故障时刻；至少保存多次独立随机试验，并报告全部回合。阈值和时间窗口在验证集固定。失败回合按截止时间未恢复统计，不能删除后只计算成功样本的平均恢复时间。时序输入、地图坐标与评分对齐方式公开。

主动运动会改变后续观测，须另做闭环测试，不能声称与被动回放共享同一扫描序列。性能较差的原库方法先核对原协议、训练预算和平台适配，不把适配错误当作算法局限。

## 交付与记录

作者原库复现证据保存在 `results/reference/<method>/`。机器人测试的原始 bag／点云与完整日志保存在被忽略的 `results/runs/robot-tests/`；通过验收的轻量报告、地图、指标与媒体保存到 `results/robot-tests/reference/`。

每回合至少记录上游提交、机器人／传感器哈希、场景因素、路线、故障时刻、有效约束重现时刻、输入哈希、算法配置、训练范围、随机种子、退出码和全部输出。GIF／MP4 标注实录或数据回放，保留失败与负结果。

第一阶段成果是**原库复现记录＋逐级建图与定位测试＋开放问题的失效／恢复分析**。具体恢复策略由证据选择，测试协议不预先指定新算法。
